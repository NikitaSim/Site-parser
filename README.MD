# Parser — сервис парсинга товаров и AI-поиска

Сервис на Go, который:

1. Парсит каталог товаров с сайта `nprommet.ru` и сохраняет их в PostgreSQL.
2. Принимает пользовательские запросы в свободной форме («нужна металлическая лавочка до 15000») и через локальную LLM (Ollama, `qwen3:8b`) превращает их в структурированный фильтр, ищет подходящие товары в БД и дополнительно ре-ранжирует их через LLM.

## Архитектура

```
                 ┌─────────────┐
   HTTP запрос → │   handler   │  (net/http, POST /parse, POST /chat)
                 └──────┬──────┘
                        │
                 ┌──────▼──────┐
                 │   service   │  бизнес-логика: парсинг, чат, ре-ранжирование
                 └───┬─────┬───┘
                     │     │
          ┌──────────▼┐   ┌▼───────────┐
          │  parser   │   │ repository │
          │ (goquery) │   │  (pgx v5)  │
          └──────────┬┘   └────────────┘
                     │
              nprommet.ru                  ┌────────────┐
                                           │  ai.Client │──▶ Ollama (/api/chat)
```

Слои строго разделены по пакетам (`internal/handler`, `internal/service`, `internal/parser`, `internal/repository`, `internal/ai`, `internal/models`), каждый общается с соседним через интерфейс (`Service`, `Repository`, `Parser`, `ClientService`).

## Инфраструктура (docker-compose)

Поднимаются 4 сервиса:

| Сервис     | Назначение                                              | Порт (снаружи → внутри) |
|------------|----------------------------------------------------------|--------------------------|
| `postgres` | БД товаров, инициализируется `init.sql`                  | `5433 → 5432`            |
| `parser`   | сам Go-сервис (сборка из `Dockerfile`, зависит от `postgres`) | `${PORT} → 8080`     |
| `n8n`      | визуальный оркестратор сценариев, зависит от `parser`     | `5678 → 5678`             |
| `ollama`   | локальный инференс LLM                                    | `11434 → 11434`           |

Health-check есть у `postgres` (`pg_isready`) и `n8n` (`wget --spider /healthz`).

## База данных

Таблица `product` (см. `init.sql`):

```sql
CREATE TABLE IF NOT EXISTS product(
    id BIGSERIAL PRIMARY KEY,
    product_name TEXT,
    category TEXT NOT NULL,
    price INTEGER,
    info TEXT,
    product_description TEXT,
    link TEXT
);

CREATE INDEX idx_product_category ON product(category);
```

- Индекс по `category` ускоряет фильтрацию по категориям в `GetProducts`.
- Поле `link` — уникальный идентификатор товара де-факто (используется парсером для получения описания).

## API

### `POST /parse`

Запускает полный цикл парсинга сайта и сохранения товаров в БД.

- Обёрнут в `RecoverMiddleware` (перехват паники) и `LoggingMiddleware`.
- Вызывает `service.Parse()`:
  1. `repo.ClearData()` — **полная очистка таблицы `product`** перед новым парсингом.
  2. Параллельный обход категорий и товаров сайта (`parser.Parse`).
  3. Батчевая вставка товаров через `SaveBuffer` (пачками по 100).
- Ответ: JSON `ParseResults` — `{categories, parsed, inserted, errors}`.

### `POST /chat`

Принимает `{"message": "текст запроса"}` и возвращает список подходящих товаров.

Пайплайн (`service.Chat`):
1. Отправка сообщения в LLM с `ai.SystemPrompt` → получение JSON-фильтра (`categories`, `keywords`, `priceMin/Max`, `needClarification`).
2. Поиск товаров в БД (`repo.GetProducts`) с последовательным ослаблением фильтра, если ничего не найдено: сначала убираются категории, затем цена, затем ключевые слова.
3. Найденные товары прогоняются через `DescriptionFilter` — рекурсивное ре-ранжирование через LLM с промптом `ai.RerankPrompt`: батчи по 15 товаров отправляются в LLM, которая отбирает подходящие; если в ответе >5 товаров — батч делится пополам и уходит на следующий уровень (`Level`) для повторной фильтрации.
4. Итоговый список возвращается клиенту как JSON.

## Логика парсинга

`parser.Parse` (пакет `parser`):

1. Загружает главную страницу и извлекает список категорий (`GetCategories`, селектор `#catalogMenu a`).
2. Категории раздаются 4 воркерам через канал `job`; каждый воркер грузит страницу категории и извлекает товары (`GetProducts`, селектор `.product`).
3. Товары уходят в канал `product` (буфер 32), который разбирают 15 воркеров: для каждого товара догружается описание со страницы товара (`GetDescription`, селектор `.productTabsContent`) и товар с описанием отправляется дальше в основной канал `ch`.
4. `service.Parse` читает `ch` тремя `batchWorker`, которые копят товары по 100 штук и сохраняют одним batch-insert (`SaveBuffer`).

Итого используется 3 уровня конкурентности: обход категорий (4 горутины) → сбор товаров (product-канал) → догрузка описаний (15 горутин) → батч-сохранение (3 горутины).

## AI-промпты

- **`SystemPrompt`** — превращает свободный текст пользователя в строгий JSON-фильтр (`categories`, `keywords` в виде массива синонимических групп, `priceMin/Max`, `needClarification`). Жёстко ограничивает список допустимых категорий и запрещает придумывать новые.
- **`RerankPrompt`** — принимает батч товаров вместе с запросом пользователя и возвращает только те, что реально подходят, отсортированные по релевантности, без изменения полей — просто JSON-массив.

Оба промпта требуют "голого" JSON без markdown-обёрток — на стороне кода это подчищается функцией `service.NormalizeJSON` (обрезает `` ```json `` и всё, что до первой `[`/`{` и после последней `]`/`}`).

## Запуск проекта

```bash
# 1. Создать .env со всеми переменными из раздела выше
# 2. Поднять инфраструктуру
docker compose up -d --build

# 3. Убедиться, что модель загружена в Ollama
docker exec -it ollama ollama pull qwen3:8b

# 4. Запустить парсинг
curl -X POST http://localhost:${PORT}/parse

# 5. Сделать запрос в чат
curl -X POST http://localhost:${PORT}/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "нужна металлическая лавочка до 15000"}'
```
